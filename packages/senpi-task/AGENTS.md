## CONVENTIONS

- Private TypeScript-source package, sideEffects:false, optional Senpi/TypeBox peers; isolate host imports from pure state/store/schema modules. Do not import omo-opencode here.
- task is spawn-only, taking one prompt or nonempty tasks batch; task_send handles steering/revival/team/shutdown traffic and task_output reads status/transcripts.
- buildLeadTeamTools returns team_create, team_delete, task_create, task_get, task_list, task_update in order; child/member sessions never receive lead lifecycle/tasklist tools, only scoped task_send for members.
- In-process children share filtered parent tool closures, remove task/team and UI-only tools, expose x_search directly, and persist conversations under the same children/<task>/sessions layout as process mode. Completion defaults to final-text; turn supports tool-only children.
- Team members always use process mode. Host sessions belong to the parent session tree; descendants reuse its shard, revived children use the recorded socket, and OMO_RPC_SOCKET* route operator/thread traffic only. daemon-launch-spec.json is the only host argv source.
- Resolve auto once from a capable reachable host; unresolved auto means in-process. Explicit user and per-agent modes win; host fallback is limited to documented mismatch/platform/runtime conditions.
- Store state defaults under the canonical agent project directory while preserving an existing project .omo/senpi-task; task.state_dir overrides. list prunes vanished cache entries; append handles use a capped pool.
- Agent overlays apply markdown, programmatic definitions, then omo.json fields. Curated readonly agents stay in-process, use a validated read-only shell broker, and are rejected as team members; an empty allowlist means no tools.
- Agent model resolution applies an explicit override, agent model/models, ordered categories (model selection only), then curated builtin chains. Disabled agents stay unavailable even with an explicit model. The three native reviewer identities keep category chains and report-write access, separate from curated readonly names.
- Plan-consultant/reviewer require USER-requested ulw-plan, a touched .omo/plans artifact at any root, and no ulw-execute invocation; absent tracking fails closed. Check forbidden skills first; never let a model unlock the gate itself or send to a one-shot plan reviewer.
- Categories require both their listed-model gate and a viable chain; explicit category config bypasses builtin activation gates. Gateway republishes never satisfy provider-bound rungs. Never resolve outside the category's chain; models[] outranks legacy fields, subscription providers rank first, and mirrored chains retain parity tests.
- Category descriptions cannot consult the registry at registration: annotate gated names, then enforce gates at spawn. Provider prompt appends dispatch by model family; retain the deep-low escalation contract without inventing routing targets.
- Team send first persists unread mail, reserves .delivering-<id>, and commits processed/<id> only after recipient-session observation. The incremental session-marker index is authoritative; member pollers run in-child, and owned-lead polling pauses during compaction/switch/shutdown.
- Completion dedupes by (task_id,run_epoch): only externally caused completed/error/lost push; caller cancel/interrupt returns synchronously. Idle wakes and streaming delivery are unconditional; compaction/switch/shutdown buffers. Adapter batching must not suppress, delay, or split notifications.
- enqueue means queued, not delivered. Failed or dropped batches must call recordDeliveryFailure to roll back optimistic notified_epoch, stamp failure, and retry; notification bookkeeping mutates only epochs under the conditional record mutation.
- Recovery order is buffered completion flush/drop, scoped reconciliation, member liveness, reservation reclaim, unnotified redelivery, awaited TTL, owned-lead poll, then status. Dead members resume persisted sessions without replaying their original prompt.
- Shutdown suspends all owned handles AND pending records on every reason. Forget registry ownership before abort/terminate/dispose so late outcomes cannot overwrite suspended state. Preserve status/epochs/stats, clear in-process pids, retain process pids for orphan proof; resume_children:false retains dispose-all behavior.
- Killed/cancelled/lost children use destruction and never revive. Suspended children cannot be woken by task_send; resume the owning session. SpawnSpecV1 contains plain launch facts only, never executable tools/auth/registries; discard untrusted legacy extensions/member_env.
- Reconcile revives only the resumed session's children; undefined session id runs the legacy crash sweep. Check foreign-live ownership before every mutation. Reclaim orphan residents through owner CAS without consuming a new slot; admit parked records under a per-session lease, nonterminal first, then updated_at descending/task_id ascending. Overflow stays suspended with deferred/capacity.
- Admission lease is token-owned and renewable: one-second refresh, stale takeover after three intervals under CAS, isOwner before mutation, own-token release only. Acquisition is bounded to five seconds and defers on contention; never hold the lease across respawn IO.
- Suspension never increments run_epoch; nonterminal reattach increments once, terminal reattach never does. Retryable respawn restores prior residency; unrecoverable terminal records dispose with results retained. Require exact persisted provider/model for in-process resume, never substitute a model.
- Never relaunch a terminal without transcript. A nonterminal with no session file may launch its v1 prompt once, then drain durable steering; no file/spec becomes lost. Prove an orphan RPC pid dead before replacing it. Only an actually interrupted nonterminal tail gets a continuation nudge, reading beyond an oversized final JSONL line when necessary.
- TTL first revalidates retention and tombstones under the record lock, then destroys/deletes outside it. Resume phase two for crash leftovers; tombstones never resurrect. Retain live handles/claims, nonterminals, owed notifications, and lost process records until pid death is proven.
- Lifecycle is the sole destruction writer. Steering uses manager-owned ports and outcome unions, fences internal epochs inside mutations, emits steer_dropped for queue clearing, and never replays admitted workpool assignments as individual sends.
- DAG admission follows completed dependency frontiers and free slots; compiled waves are informational. Amend settled-node changes through the DAG manager rather than retrying a completed node.
- Isolation preparation refuses an uncloneable checkout; missing isolation wiring refuses isolated spawn. Crash salvage retains artifacts and never auto-merges unreviewed deltas.

## ANTI-PATTERNS

- Never dispose/terminate/SIGTERM directly from steering, revive an accepted cancellation, or automatically resend delivery_uncertain transport outcomes.
- Never replace a live owner's state, replay an original prompt on session reattach, or persist executable launch inputs.
- Never test concurrency with sleeps or timing luck; co-located tests use given/when/then, injected clocks and event subscriptions.

### Category activation gating

A builtin category may declare `requiresModel` (a bare model id, or a list of ids any one of which satisfies it; `categoryGateModels` returns the normalized list) in its `BuiltinCategoryDefinition`. `resolveCategory` treats such a category as unavailable - `model_unavailable`, excluded from `availableCategories`, and never routed through its fallback chain - unless the gate model is present in the live senpi registry. ANY explicit `omo.json` `categories.<name>` entry bypasses the gate, even a description-only one, mirroring `hasExplicitUserConfig` in `packages/omo-opencode/src/tools/delegate-task/categories.ts`. A gate, like a chain rung, counts only a registry model served by a provider the category's chain lists: a gateway re-publishing the model (`openrouter/anthropic/claude-opus-5.5`, `vercel/openai/gpt-5.6-sol`) opens nothing and is never selected, so a gateway-only machine sees the builtin as unavailable (#9146). `deep-low` gates on exactly `gpt-6.2-sol` (no older Sol and no Fast tier) and `deep-high` on exactly `gpt-6.2-astra`, each confined to its own family, so a registry missing one lane drops it instead of serving the other lane's model under its name. Four builtins are gated today: `architect` on `claude-fable-5`, `ultrabrain` on the GPT flagship pair `gpt-6-astra` OR `gpt-5.6-sol` (`requiresModel` accepts one id or a list; any listed id present in the registry opens the gate, so a registry carrying either flagship keeps `ultrabrain` while a registry with neither never falls through to a cross-family model), and the two deep lanes on their own single ids. Each gated builtin keeps a fallback chain confined to its own family; `openai-categories.ts` also owns `unspecified-high` (default `anthropic/claude-opus-5-5` max, ungated, chain `claude-opus-5-5` → `glm-5.3` → `kimi-k3`; it keeps its Astra prompt-append hook for a user override onto a GPT-6 model). The GPT defaults name `chatgpt-subscription`; every GPT rung lists `chatgpt-subscription` first and `openai` (senpi's API-key lane, or an OpenAI-compatible proxy under that id) directly after it, so the subscription wins when both serve the model (#8300) and an `openai`-only machine still reaches every GPT rung at selection and in the runtime fallback list, which walks listed providers only (#8734).

A **second, independent gate** runs alongside `requiresModel`: `isCategoryChainViable` (`category/builtins.ts`) drops any builtin whose fallback chain has zero rungs resolvable against the live registry. This applies to ALL builtins, not just the three with `requiresModel` - against a registry holding only an unrelated model, `resolveAvailableCategoryNames` returns `[]`. `resolveAvailableCategoryNames(config, registry)` (`category/resolver.ts`, re-exported from the barrel) is the public entry for the gated list; it degrades to the ungated list if the registry call throws.

The task tool description cannot consult the registry - it is built at tool registration, before the model registry is captured - so `listTaskCategories` keeps gated builtins listed and appends a ` (requires <model>)` annotation instead. A category carrying an explicit `omo.json` entry is listed without the annotation. Spawn-time `resolveCategory` remains the sole authoritative gate.

### Plan-gated agents

## TEAM DELIVERY MODEL

Team messaging is injection-driven over durable mailboxes. A send writes a durable unread JSON file and returns; delivery steers the message into the recipient's running turn without queuing an editable follow-up. The current lead owns one `createLeadPoller` per team whose durable `leadSessionId` matches the current session. The adapter ticks owned lead pollers on `session_start` and every second, but suspends ticks during compaction, session switching, and shutdown. Member inboxes are never polled by the adapter: each process member loads `member-extension/`, which owns that member's poller and scoped tools inside the child process.

Delivery is reservation-based: unread `<messageId>.json` becomes `.delivering-<messageId>.json`, then commits to `processed/<messageId>.json` only after the message is observed in the recipient session (the pre-injection `team_wait` claim path was removed). The processed file is the durable exactly-once ledger.

Persistence of the delivered `peer_message` envelope in the lead's session JSONL is checked by `createSessionMarkerIndex` (`team/messaging/session-marker-index.ts`): a per-path incremental byte-offset index that reads only bytes appended since the last check, so the many `messageId` lookups per tick are O(1) instead of re-reading and re-parsing the whole file. It handles file truncation/rotation by rescanning from zero, and reads nothing when the file has not grown.

Every `session_start` runs the durable recovery chain in order: flush or drop buffered completions, reconcile (revive the resumed session's suspended children; reattach durable process members), re-observe owned-member liveness, reclaim stale member and owned-lead reservations, redeliver unnotified completion notifications, await TTL cleanup, then poll owned leads and sync status. Dead process members with a persisted session are respawned without replaying their original prompt and rebound with `switch_session`; set `task.reattach_on_reconcile: false` only to retain the old lost-task behavior.

### Completion routing table (`completion/routing.ts`)

`shouldNotifyStatus` fires only for externally-caused terminals `completed`/`error`/`lost` (`routing.ts:4`); parent-initiated cancel/interrupt return synchronously in the tool result and never push. `routeCompletion` maps parent state to an action: `idle` -> `wake` and `streaming` -> `deliver_streaming`, both delivered unconditionally (no setting may suppress, delay, or split them - the omo-senpi coordinator batches every notification ready in the same window into ONE injection steered into the running turn at the next tool-call boundary), and `compacting`/`session_switching`/`session_shutdown` -> `buffer` until the parent settles (`routing.ts:12`).

## EXECUTION MODES

- **in-process (default)**: `InProcessRunner` runs the child through the SAME parent tool closures (`filterSharedParentTools` + `mergeChildCustomTools`), so a child sees the parent's live custom tools minus the `task_*`/`team_*` family. Shared-tool rules live in `src/runners/in-process/shared-tool-filter.ts`: `uiOnlyToolNames` drops parent-only tools (omo-senpi passes the memory tools), and `CHILD_DIRECT_EXPOSURE_TOOL_NAMES` currently remaps `x_search` from `exposure: "search"` to `"direct"` because children have no `tool_search` builtin. Child conversations persist under the same `<stateDir>/children/<taskId>/sessions/` layout as process mode, so a clean quit and a crash recover identically. `ChildSpec.completion` defaults to `final-text`; `turn` treats a normally settled turn as completion for tool-only children. Proven by the marker-tool test (`src/runners/in-process/marker-suppression.test.ts`).
- **process**: `RpcProcessRunner` spawns a child Senpi process; steering (`steer`/`abort`/`prompt`) crosses a JSON-RPC boundary (`src/runners/rpc/protocol-client.ts`), child transcripts land under `<stateDir>/children/<taskId>/sessions/<taskId>/`, and session-start reconciliation can respawn and `switch_session` to the newest persisted JSONL. Team members always use this mode so the member extension and durable inbox poller live inside the child.

- **process via the daemon (`task.process_runner: host`)**: `RpcHostRunner` (`src/runners/rpc-host/`) opens the child as a SESSION inside its parent session's own engine host (one host per session tree, `<shardRoot>/p-<shardKey("p", rootSessionId)>.sock`, `rpc-host/shard-socket.ts`) instead of spawning a process. A new child asks the runner's `shardResolver`; a child opened inside a host carries `tree_key`/`shard_key` in its session context, so its own children attach to that same host and never ensure it; a revived or reattached child opens only on the socket its record names. `OMO_RPC_SOCKET*` never route children: `resolveTaskHostSocket` (`rpc.sock` or the override) serves the operator commands and the thread tools only. `ensureTaskDaemon` probes the socket, asks the engine's `decideHostAction` what to do (reuse / start / handoff / refuse) and delegates the ensure to `senpi host`; the launch spec at `<pluginRoot>/daemon-launch-spec.json` is the ONLY argv source. Steering crosses the same JSON-RPC boundary; retained sessions survive a parent quit and re-attach on resume without prompt replay. Falls back to `child-process` only for a capability/policy `engine_mismatch`, on win32, or on a bun-less Node (`HostUnavailableError`).

Mode is chosen by `resolveExecutionMode` from the omo.json `task.default_execution_mode` and per-agent `execution_mode` (`src/manager/execution-mode.ts`). `auto` is resolved ONCE per parent session at its first ensure of its own task host: a reachable host that advertises session kind/context + retain + the host protocol -> `process`/`host`; otherwise in-process. Unresolved `auto` reads as in-process (never route on a guess); a user-set mode and every per-agent override win over the host check. Operator surface: `omo daemon run|adopt|status|stop|handoff|gc|rollback-prepare`, every command but `run` (the operator endpoint) and `adopt` (one host session into a terminal) covering every endpoint (`docs/reference/omo-daemon.md`).

## SESSION SUSPEND AND RESUME REVIVAL

Shutdown suspends instead of disposing. `suspendOnSessionShutdown({parentSessionId, reason})` (`lifecycle/shutdown.ts`) runs on every `session_shutdown` reason (`quit`/`reload`/`new`/`resume`/`fork`): live handles are still torn down (no-orphan law) but the records survive as `persisted_only` (in-process; clears `host_pid` and the last `pid`) or `rpc_detached` (process; keeps the last `pid` for orphan detection), with status, epochs, and run stats preserved and a `suspended` event appended carrying the reason. The scan covers TWO populations - every registry handle AND this session's `pending` records (a queued child has no handle and no session file yet, so a handle-only scan would strand it; pending records are dequeued and parked `persisted_only`) - matched on `parent_session_id === parentSessionId && host_pid === context.hostPid`. A deliberately-stopped child (`killed === true`, a durable record fact independent of status, or a `cancelled`/`lost` status) routes through the destruction port with the `cancel` cause and never revives. Per handle the order is: registry forget FIRST (stale outcome tracking loses ownership before `abort()` settles the turn, so no `cancelled`/`error` terminal can land on the suspended record), best-effort abort, rpc terminate, dispose, residency transition. `task.resume_children: false` runs the pre-feature dispose-all path unchanged.

Revival state lives on the record. `spawn_spec` is a union (`state/types.ts`): the legacy `{cwd}` process shape (persisted `extensions`/`member_env` are discarded as untrusted launch inputs) still feeds RPC respawn, while `SpawnSpecV1` (`{version: 1, cwd, prompt, instructions?, member_scoped_tool_names?}`, guard `isSpawnSpecV1`) carries only plain-data launch facts - never executable tools, auth, or registries - and is REQUIRED for in-process rebuild (`spawn_spec_unavailable` otherwise). `notify_on_terminal` persists the intent to notify the parent at a terminal state (set from `run_in_background` at spawn, persisted by `promoteToBackground`). `pending_steering` is the durable prelaunch queue, drained in persisted order when the child starts; `task_send` to a suspended child returns `not_continuable` ("suspended - resumes when its session is resumed") because messaging a suspended child must not wake it - resume its session instead.

`reconcileOnSessionStart(parentSessionId)` revives ONLY that session's children; called with `undefined` it runs just the legacy global crash sweep, and legacy resident orphans of OTHER sessions keep the pre-feature reattach/lost behavior either way. A foreign-live-owner guard runs for every status before anything mutates. Candidates split into two disjoint populations (`lifecycle/reconcile-revival.ts`, `lifecycle/residency.ts`). RECLAMATION covers orphaned `resident` records (dead owner, or `host_pid === self` with no live handle after a same-process switch): they already occupy a slot, so they bypass the capacity gate and are claimed by a per-record expected-owner CAS (`reclaimOrphanedResident`), and a `killed: true` orphan is disposed so it releases its slot. ADMISSION covers `persisted_only`/`rpc_detached` records needing a NEW slot, claimed as a batch under the per-parent-session admission lease with deterministic selection (non-terminal first, then terminal by `updated_at` DESC, tie-break `task_id` ASC) up to the free `residency_max_children` slots. Overflow stays suspended with `deferred/capacity` - never evicted, never lost.

The admission lease (`lifecycle/admission-lease.ts`, `<stateDir>/locks/session-<parentSessionId>.lock`) is a renewable owner-token lease `{pid, token, renewed_at}`. The holder refreshes `renewed_at` every second; takeover of a lease stale past three refresh intervals is a token CAS under the short record mutex (re-validating token AND staleness, never delete-then-create); the holder re-checks `isOwner()` before every mutation; release removes the file only while the token is still its own. A bounded 5s acquisition yields `deferred/lock_contended` for the whole batch instead of aborting session start. The critical section holds only record reads and `store.mutate` claims; all respawn I/O runs after release.

Outcomes add a `deferred` kind with reason codes `capacity`/`lock_contended`/`foreign_live_owner`/`model_unavailable`/`tools_unavailable`/`session_unavailable`/`spawn_spec_unavailable`/`team_inactive`/`reattach_disabled`/`rollback_failed` (`lifecycle/types.ts`). A retryable respawn failure rolls the claim back to the prior suspended residency and defers; an unrecoverable one disposes a terminal record (persisted result preserved) or marks a non-terminal one `lost`. Suspension never bumps `run_epoch`; a non-terminal reattach bumps it exactly once, a terminal reattach never. Respawn dispatches on `execution_mode` (`manager/manager-respawn.ts`): process children ride the existing RPC respawn, in-process children go through `InProcessRunner.resume` over the persisted session, gated by a fail-closed resolver that matches the persisted `resolved_model` provider + model_id exactly and otherwise yields `deferred/model_unavailable` - never a substitute model. No-rerun rules: a terminal record without a transcript is disposed, never relaunched; a non-terminal record without a session file relaunches exactly once from its persisted v1 prompt (senpi writes no JSONL before the first assistant message, so no work is re-run) and then drains `pending_steering`; only a record with neither file nor v1 spec falls to `lost`. An orphaned rpc record still carrying a live pid is terminated and proven dead before its replacement spawns. After revival only a child interrupted mid-turn receives the continuation nudge: the tail check (`manager/interrupted-turn.ts`) reads the ACTUAL last JSONL record (growing past the 64 KiB window when the final line is oversized), counts an assistant `stopReason: "aborted"` as interrupted, and never fires on a terminal record. Status surfaces label both suspended residencies `suspended` (`task_output` adds "suspended (resumes with session)").

Completion recovery rides the same session start: `reconcileUnnotifiedNotifications({sessionId, parentState})` (`completion/notifier.ts`, kept aliased as `reconcileFailedNotifications`) redelivers every terminal child of the resumed session that still owes a notification - the `notify_on_terminal` population (`notified_epoch < run_epoch`) AND legacy records whose only marker is a `notification_failed_epoch` - through the normal delivery path, dedupe identity `(task_id, run_epoch)`. Notification bookkeeping patches ONLY the epochs through a conditional `store.mutate`, so a concurrent residency/`host_pid` claim is never clobbered.

Delivery is BATCHED on the adapter side (omo-senpi's idle-injection coordinator), so a returning `ParentNotifier.enqueue` means QUEUED, not delivered, and `notified_epoch` is persisted optimistically at that point. `recordDeliveryFailure({taskIds, error})` is the out-of-band receipt for a queued notification that never landed - a failed flush, or a batch window dropped when the coordinator retires on `session_shutdown`/`/reload`: it rolls `notified_epoch` back below the epoch, stamps `notification_failed_epoch`, appends `notification_failed`, and re-enters the retry ladder, which is exactly what keeps the reconcile above from skipping the record forever (`notified_epoch >= run_epoch`) and losing the completion. A refused enqueue (retired coordinator) throws instead and takes the same failure path synchronously.

TTL deletion is a two-phase tombstone (`lifecycle/ttl.ts`): phase 1 inside the record lock re-validates the retention predicate against a fresh read and renames the record to `<taskId>.json.expunging` (invisible to `load`/`list`, so no revival claim can take it); phase 2 outside the lock destroys a live orphan rpc pid (`ttl` cause), deletes the children dir, spill, and log, then drops the tombstone. Every sweep first completes phase 2 for tombstones a crashed sweep left behind - a tombstoned record is committed to deletion and never resurrected. The retention predicate keeps records with a live registry handle, a live host claim (a foreign owner OR this process's fresh claim inside the claim/respawn window), any non-terminal status (a suspended child in flight is never TTL-deleted), an undelivered terminal notification from either population above, and `lost` process records until their pid is proven dead.
